# Inception

## Description

Inception is a system administration project from the 42 curriculum. The goal of the project is to build a small infrastructure using Docker Compose and several custom Docker images.

The infrastructure is composed of three services:

* **NGINX**: the only entry point to the infrastructure. It accepts HTTPS connections on port 443 and uses TLSv1.2 and TLSv1.3.
* **WordPress + PHP-FPM**: provides the WordPress website and executes PHP through PHP-FPM.
* **MariaDB**: provides the database used by WordPress.

The services run in separate Docker containers and communicate through a dedicated Docker network.

The project uses:

* Docker Compose
* Debian Bookworm
* NGINX
* PHP-FPM
* WordPress
* MariaDB
* Docker named volumes
* Docker secrets
* Environment variables
* TLS certificates
* A dedicated Docker network

The final architecture is:

```text
                         HTTPS :443
                              |
                              v
                    +------------------+
                    |      NGINX       |
                    |     TLS 1.2/1.3  |
                    +--------+---------+
                             |
                             | FastCGI :9000
                             v
                    +------------------+
                    |    WordPress     |
                    |    PHP-FPM       |
                    +--------+---------+
                             |
                             | MySQL :3306
                             v
                    +------------------+
                    |     MariaDB      |
                    +------------------+

             All services are connected through
                  the Docker "inception" network.
```

## Services

### NGINX

The NGINX container is based on Debian Bookworm.

NGINX is configured as the only public entry point. Port 443 is exposed by Docker and HTTPS is enabled using TLSv1.2 and TLSv1.3.

The NGINX configuration forwards PHP requests to the WordPress container through PHP-FPM on port 9000.

The certificate and private key are generated by the container initialization script when they do not already exist.

NGINX serves the WordPress files from the shared WordPress volume in read-only mode.

### WordPress and PHP-FPM

The WordPress container is also based on Debian Bookworm.

It contains:

* PHP-FPM
* PHP MySQL support
* PHP cURL
* PHP GD
* PHP mbstring
* PHP XML
* PHP ZIP
* WP-CLI

WordPress is installed into `/var/www/html`.

At startup, the initialization script:

1. Reads the database password from Docker secrets.
2. Creates `wp-config.php` if it does not exist.
3. Checks whether WordPress is already installed.
4. Installs WordPress when necessary.
5. Creates the configured administrator and editor user.
6. Starts PHP-FPM in the foreground.

PHP-FPM listens on port 9000 inside the Docker network.

### MariaDB

The MariaDB container is based on Debian Bookworm.

The initialization script:

1. Initializes the MariaDB data directory when necessary.
2. Starts MariaDB temporarily without networking during initialization.
3. Creates the WordPress database.
4. Creates the WordPress database user.
5. Grants the required privileges.
6. Sets the MariaDB root password.
7. Shuts down the temporary server.
8. Starts MariaDB normally.

MariaDB listens on the Docker network and is not directly exposed to the host.

## Docker

Docker is used to isolate each service into its own container.

Each service has its own Dockerfile and is built locally using Docker Compose. No ready-made application image is used as the final service image.

The three application images are built from Debian Bookworm:

```text
Debian Bookworm
       |
       +---- NGINX image
       |
       +---- WordPress/PHP-FPM image
       |
       +---- MariaDB image
```

Docker Compose manages:

* service creation
* image building
* container networking
* persistent storage
* Docker secrets
* restart policies

## Main design choices

### Separate containers

Each main service runs in its own dedicated container.

This follows the architecture required by the project and keeps NGINX, WordPress/PHP-FPM and MariaDB separated.

### Dedicated Docker network

The three services communicate through the `inception` Docker network.

The services use their Docker Compose service names for internal communication:

```text
NGINX -> wordpress:9000
WordPress -> mariadb:3306
```

No host networking or Docker legacy links are used.

### HTTPS only

NGINX is the only service exposed to the host:

```yaml
ports:
  - "443:443"
```

WordPress/PHP-FPM and MariaDB are only accessible through the Docker network.

TLS is restricted to:

```text
TLSv1.2
TLSv1.3
```

### Environment variables and secrets

Non-sensitive configuration is stored in `srcs/.env`, including:

```text
DOMAIN_NAME
MYSQL_DATABASE
MYSQL_USER
```

Sensitive information is stored using Docker secrets:

```text
secrets/
├── credentials.txt
├── db_password.txt
└── db_root_password.txt
```

The containers access these values through `/run/secrets/`.

Passwords are therefore not stored directly in Dockerfiles or the Docker Compose configuration.

## Required comparisons

### Virtual Machines vs Docker

A virtual machine emulates or virtualizes a complete computer environment, including its own operating system kernel.

Docker containers share the host operating system kernel and isolate applications and their dependencies at the process level.

For this project, Docker is appropriate because the goal is to build a small multi-service infrastructure where each service runs in its own isolated container.

A simplified comparison is:

| Virtual Machine               | Docker                                 |
| ----------------------------- | -------------------------------------- |
| Includes a complete guest OS  | Shares the host kernel                 |
| Usually heavier               | Usually lighter                        |
| Strong system-level isolation | Application/process isolation          |
| Requires more resources       | Generally requires fewer resources     |
| VM images are larger          | Container images are generally smaller |

### Secrets vs Environment Variables

Environment variables are convenient for configuration values such as:

```text
DOMAIN_NAME
MYSQL_DATABASE
MYSQL_USER
```

They are not designed to be the preferred storage mechanism for sensitive credentials.

Docker secrets are used in this project for passwords and credentials. They are mounted into the containers under `/run/secrets/`.

Therefore:

```text
Configuration
    -> environment variables

Sensitive credentials
    -> Docker secrets
```

### Docker Network vs Host Network

With a Docker network, containers communicate through an isolated Docker networking environment.

In this project, the services communicate through the `inception` network:

```text
nginx
  |
  +---- wordpress
          |
          +---- mariadb
```

Host networking would make a container use the host's network namespace directly.

The project explicitly requires a Docker network and forbids `network: host`, so the stack uses a dedicated Docker bridge network.

### Docker Volumes vs Bind Mounts

Docker volumes provide Docker-managed persistent storage that exists independently from the lifecycle of a container.

Bind mounts directly map a host filesystem path into a container.

This project uses named Docker volumes for the WordPress and MariaDB persistent data, with their storage configured under:

```text
/home/mgrandia/data/mariadb
/home/mgrandia/data/wordpress
```

The WordPress volume contains the website files and the MariaDB volume contains the database files.

The exact volume configuration is defined in `srcs/docker-compose.yml`.

## Instructions

### Prerequisites

The project requires:

* A Linux virtual machine
* Docker
* Docker Compose
* GNU Make
* Sufficient permissions to run Docker

The project must be run from the repository root.

### Build and start the project

The default command is:

```bash
make
```

This builds the images and starts the containers in detached mode.

The equivalent explicit command is:

```bash
make up
```

### Build without starting

```bash
make build
```

### Stop the containers

```bash
make down
```

### Stop containers and remove volumes

```bash
make clean
```

### Remove containers, volumes and images

```bash
make fclean
```

### Rebuild the complete infrastructure

```bash
make re
```

### View logs

```bash
make logs
```

### Check the Compose services

```bash
make ps
```

### Access the website

The configured domain is:

```text
https://mgrandia.42.fr
```

The WordPress administration interface is available through:

```text
https://mgrandia.42.fr/wp-admin
```

The browser may warn about the TLS certificate because the project generates a self-signed certificate for the local infrastructure.

## Persistent data

The project uses two persistent storage areas:

```text
/home/mgrandia/data/mariadb
/home/mgrandia/data/wordpress
```

The MariaDB storage contains the WordPress database.

The WordPress storage contains the WordPress website files.

This allows the application data to persist independently of the lifecycle of individual containers.

## Security

The project follows several security-related requirements:

* Only port 443 is exposed by the infrastructure.
* TLSv1.2 and TLSv1.3 are enabled.
* Database passwords are provided through Docker secrets.
* WordPress credentials are provided through Docker secrets.
* Secrets are kept outside the Dockerfiles.
* `.env` contains non-sensitive configuration.
* The WordPress volume is mounted read-only in the NGINX container.
* MariaDB is not exposed directly to the host.

Sensitive credentials must never be committed to the Git repository.
